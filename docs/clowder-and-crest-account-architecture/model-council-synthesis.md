# Model Council Synthesis — Clowder & Crest Cloud Save Sync

**Consulted at Deep Dive depth:** Claude Opus 4.8, GPT-5.5, Gemini 3.1 Pro.

This synthesis compares the three independent implementation plans for adding account-based cloud save sync to *Clowder & Crest*. All three models read the same source materials (Clowder's `SaveManager.ts`, Quadrille brief, Chart35 incident notes, infrastructure ADRs, career plan) and arrived at strikingly convergent architectural conclusions, with the meaningful differences appearing in depth of safety mechanics, schema choices, and operational specificity.

---

## 1. Where Models Agree

| Finding | Claude Opus 4.8 | GPT-5.5 | Gemini 3.1 Pro | Evidence |

## 2. Where Models Disagree

| Topic | Claude Opus 4.8 | GPT-5.5 | Gemini 3.1 Pro | Why They Differ |
|---|---|---|---|---|
| **Concurrency primitive** | Integer `revision` (monotonic per `(user,slot)`) + `lastPlayedTimestamp` for tiebreak/highlight | **SHA-256 hash** of canonicalized JSON as the conflict key (`baseHash`) | Integer `version` (or timestamp) | Hashes detect *content* equality (idempotent re-PUT = no-op); revisions detect *ordering*. GPT-5.5's hash approach is the most rigorous for idempotency; Opus's revision is the most operationally simple. Both work; hash gives free dedupe and clearer "same content, different metadata" handling. |
| **Server-side history of overwrites** | Not explicitly tabled (relies on client `.bak` only) | Explicit **`clowder_save_slot_versions`** table archiving every replaced cloud row with a `reason` enum (`overwrite`, `download-replaced`, `delete-cloud`, `admin`) | Not explicit (client `.bak` only) | GPT-5.5 is the most defensive: every forced overwrite is recoverable server-side. Opus and Gemini rely solely on the client backup, which is sufficient on the *device* that did the overwrite but offers no recovery if the destructive action came from a different device. |
| **Server port** | 3476 | 3486 (deliberately wider gap from Quadrille's 3475) | 3476 | Minor; pick after `ss -ltnp` shows what's free. GPT-5.5's reasoning ("document the gap") is slightly stronger for a fleet of future copy-deployed services. |
| **Service worker / `/api/` cache bypass** | Not surfaced | **Explicitly required**: add `if (url.pathname.startsWith('/api/')) return;` to `public/sw.js` as its own commit | Not surfaced | GPT-5.5 inspected `public/sw.js` and caught a real bug-in-waiting: same-origin cache-first would serve stale slot summaries. This is a concrete must-do that the other two missed. |
| **Vite dev proxy** | Not surfaced | Implicit (mentioned via CORS allowlist for `localhost:3200`) | **Explicitly recommended** — update `vite.config.ts` to proxy `/api` to `localhost:3476` so dev avoids CORS | Gemini surfaces a small ergonomic detail (no CORS in dev). Worth doing. |
| **Server save directory location** | Implies skeleton lives alongside Quadrille on the volume (skeleton-style copy-deploy) | `/var/www/clowder.stephens.page/server/` for source, venv on volume | `/var/www/clowder-sync` directory | Three different layouts. All three keep the venv on the volume, but Opus emphasizes "service code on the volume too" for the disk-pressure reason, while GPT-5.5 keeps source under the existing `/var/www/clowder.stephens.page/` tree for project locality. Either is defensible; GPT-5.5's keeps the project self-contained. |
| **Server-side save validation depth** | Light: structural gate + size ceiling (~256 KB); trusts client `validateAndSanitizeSave` on the download path | Light: shape checks (`day`, `chapter`, `cats`, lengths, `version` numeric), 1 MiB ceiling, summary extraction | Lightest: relies primarily on client sanitizer; notes a size-limit concern as an open risk | All three converge on "server is opaque storage with abuse caps," but differ in ceiling (256 KB vs 1 MiB) and how much shape-checking belongs in Python. ## 3. Unique Discoveries

| Model | Unique Finding | Why It Matters |
|---|---|---|
| **GPT-5.5** | **Service worker bypass for `/api/`** — `public/sw.js` caches same-origin GETs cache-first; without an explicit bypass, `GET /api/saves/slots` would return stale data and confuse the conflict-state machine. | This is a real bug-in-waiting that would manifest as "I uploaded, then opened the title screen, but it still says my save is out of sync." Must-fix before shipping cloud UI. |
| **GPT-5.5** | **Server-side `clowder_save_slot_versions` archive table** with a `reason` enum for every overwrite/forced replacement. | Provides cross-device recovery: if Device B clobbers Device A's cloud save and Device A had no local copy, the server still holds the previous blob. Client `.bak` alone can't recover that case. |
| **GPT-5.5** | **Content-hash conflict primitive** instead of integer revision. | Free idempotency: re-PUT of identical content returns 200 with no archive row; debounced day-end pushes that happen to send the same blob twice are no-ops by construction. |
| **GPT-5.5** | **Explicit `beforeunload`/visibility guidance** — do not start network writes from `beforeunload` (browsers cancel them); native `onPause` enqueues a pending flag instead of blocking pause. | Prevents lost-on-tab-close uploads and ANR-style native pause hangs. |
| **GPT-5.5** | **`reason` field on the PUT request body** (`day-end`/`manual-upload`/`initial-upload`/`conflict-resolution`) for server-side telemetry. | Cheap observability for diagnosing user reports. |
| **Claude Opus 4.8** | **Version-skew refusal guard** — if a downloaded blob's `SaveData.version` exceeds the client's `SAVE_VERSION`, refuse to load with a "please update the game" message. | `migrateSaveData` only migrates forward; without this guard an older device downloading a newer-client save would misinterpret fields. Concrete safety hole the other two miss. |
| **Claude Opus 4.8** | **Same-origin API is a deliberate design choice** to keep `__Host-` + `SameSite` semantics strong; deferring `api.clowderandcrest.com` is intentional, not lazy. | Surfaces an architectural decision (path-based `/api/` over a subdomain) that has security implications — moving to a subdomain later would require revisiting `SameSite=None; Secure` and CSRF. |
| **Claude Opus 4.8** | **The harvestable ADR's anti-thesis framing** — the ADR argues *against* the seemingly-more-platform-y multi-tenant design; the platform claim is earned by proving the skeleton *copy-deploys cleanly*, not by coupling apps. | This is the genuinely defensible, non-obvious trade-off that makes the ADR worth writing rather than restating an obvious choice. |
| **Claude Opus 4.8** | **`device_id` as an audit field** in the `save_slots` row ("last written by another device") for divergence UX. | Lets the chooser say "Your phone overwrote this from this device 3 hours ago" rather than just "diverged." |
| **Gemini 3.1 Pro** | **Vite dev proxy config** — update `vite.config.ts` to proxy `/api` → `localhost:3476` for local development. | Avoids dev-time CORS friction entirely; small but real ergonomic win. |
| **Gemini 3.1 Pro** | **Blob-size risk callout** — late-game `dungeonHistory` and `journal` arrays may approach the chosen ceiling. | Concrete reason to instrument blob size early and tune the ceiling. |

## 4. Comprehensive Analysis

### High-Confidence Findings

The three models converged with unusual unanimity on the architectural shape of this feature, and the convergence is itself evidence the answer is right. All three independently selected **Option A — a dedicated `clowder-sync` FastAPI service that reuses Quadrille's auth skeleton (auth.py, db.py, security.py, mailer.py) but replaces Quadrille's row-level LWW sync with a new per-slot whole-blob module** ([Claude Opus 4.8], [GPT-5.5], [Gemini 3.1 Pro]). The three justifications also agree: blast-radius isolation between two unrelated apps, fundamental sync-model incompatibility (a row-level merge of a monolithic game-state blob is logically incoherent and would produce hybrid corruption), and a stronger career story from proving the auth skeleton *copy-deploys cleanly* to a second app rather than from coupling two apps into one process. The Supabase/Firebase/Clerk alternative was rejected by all three, with Claude Opus 4.8 supplying the most operationally damning point: Supabase's free tier pauses inactive projects after one week, which is fatal for a casual game whose players return after days.

The same unanimity holds on the safety architecture, which is the most important non-architectural decision in the plan. All three models specified: optimistic concurrency with a client-supplied base (revision or hash), HTTP 409 on conflict with no silent overwrite, a mandatory user-facing divergence chooser displaying both saves with their day/chapter/cat counts and timestamps, mandatory local `.bak.<ts>` backup before any cloud-overwriting download, reuse of the existing `validateAndSanitizeSave()` as the inbound-untrusted gate, and the explicit invariant that logout or session expiry must never delete or overwrite local saves. All three traced this back to the Chart35 incident and Chart35Client's post-incident "only auto-download when no local data would be lost" rule. This is the convergence that gives the plan its strongest claim to being safe.

The transport and CORS picture also converged completely. The web side uses an httpOnly `__Host-`-scoped session cookie with `SameSite=Lax`/`Strict` (kept strong because the API stays same-origin on the path `/api/`), and the Capacitor side uses Bearer tokens stored in `@capacitor/preferences` because the WebView's origin is `https://localhost` (Android) or `capacitor://localhost` (iOS) — cross-origin to the API host, which makes the cookie path fragile. All three identified that Quadrille ships no CORS middleware because Flutter is not subject to browser CORS, and that Clowder must add an explicit-origin CORS allowlist with `allow_credentials=True` (never wildcard). The operational steps — venv on `/mnt/volume_nyc3_01/jacob/`, a new systemd unit, `ProxyPass /api/` added to **both** vhost configs, Resend sender from `noreply@stephens.page` until `clowderandcrest.com` is verified, the existing PostgreSQL 16 cluster with a new database and a scoped role — are identical across the three plans down to the shell commands.

### Areas of Divergence

The divergences are narrow but informative. The most consequential is the **concurrency primitive**: Opus and Gemini propose an integer `revision`/`version`, while GPT-5.5 proposes a **SHA-256 hash of the canonicalized JSON**. Both are correct; the difference is what they buy. A revision is operationally simpler and gives a precise "did this slot advance under me?" answer. A content hash gives free idempotency (a re-PUT of the same bytes is a no-op with no archive row, which matters because day-end debounce can fire repeatedly with the same blob), free deduplication, and naturally handles "same content, different metadata" cases. Either works, but the hash approach is the more defensive choice for a debounced-push design, and the implementation cost is a few extra lines of canonicalization.

The second meaningful divergence is **server-side overwrite history**. GPT-5.5 proposes an explicit `clowder_save_slot_versions` archive table with a `reason` enum (`overwrite`, `download-replaced`, `delete-cloud`, `admin`) that captures every replaced cloud row. Opus and Gemini rely solely on the client `.bak.<ts>` mechanism. The client backup is sufficient on the *device that did the overwrite* but offers no recovery if a different device clobbered the cloud copy. Given Clowder's explicit goal is reinstall-survivable saves — i.e., the device that wrote the cloud blob may no longer exist — the server-side archive is a meaningful belt-and-suspenders defense that costs one extra small table.

The third divergence is **coverage of incidental pitfalls**. GPT-5.5 alone caught the service-worker cache-first problem (`public/sw.js` would serve stale `GET /api/saves/slots` as a static asset) and the `beforeunload`/`onPause` network-write hazard. Gemini alone called out the Vite dev-proxy ergonomic. Opus alone caught the version-skew refusal case (older client downloading a newer-version blob must refuse, not misinterpret) and added a `device_id` audit field. None of these are architectural — they are concrete, easy-to-miss items, and a real build should adopt all of them.

A subtler divergence is **commit granularity**. Opus organizes the work as 5 server + 5 client commits and explicitly argues that the divergence chooser deserves its own commit because it's the highest-risk piece and must be independently revertible — that argument echoes the Chart35 lesson directly. GPT-5.5 breaks the work into 13 commits with separate units for the service-worker bypass, manual upload/download/compare buttons, and infrastructure files. Gemini's 7 commits are coarser. For a hobby game where the user explicitly wants atomic, bisectable commits, GPT-5.5's granularity is closest to the stated `CLAUDE.md` discipline, but Opus's argument about *why* the divergence-chooser commit must be isolated is the more important meta-point.

### Unique Insights Worth Noting

Beyond the divergences, three unique findings deserve special weight in the final plan. First, GPT-5.5's **service-worker `/api/` bypass** is a concrete shippable bug that would otherwise surface only post-launch as confusing "out of sync" UI; it should be its own atomic commit early in the sequence. Second, Claude Opus 4.8's **version-skew refusal** ("if the cloud `SaveData.version` exceeds the client's `SAVE_VERSION`, refuse to load") closes a real cross-device data-loss vector that no amount of `validateAndSanitizeSave` migration logic will catch, because the migration ladder is forward-only by design. Third, GPT-5.5's **server-side version archive** is the cheapest cross-device recovery insurance available — if the user's main concern is reinstall-safety, the device that did the destructive write may be gone, and only a server archive can recover that case.

### Recommendations

Adopt the architecture all three models converged on (dedicated `clowder-sync`, Option A on email verification, per-slot whole-blob sync, divergence chooser, `.bak` before overwrite, reuse `validateAndSanitizeSave`), and integrate the strongest unique items from each model into the final build: use **GPT-5.5's content-hash concurrency primitive** rather than integer revision (it gives free idempotency for debounced pushes), add **GPT-5.5's `clowder_save_slot_versions` server-side archive table** (cross-device recovery insurance), make the **service-worker `/api/` bypass** its own early commit, include **Claude Opus 4.8's version-skew refusal guard** as a hard rule in `CloudSync.ts`, add **Claude Opus 4.8's `device_id` audit field** so the chooser can attribute writes to specific devices, and pick up **Gemini 3.1 Pro's Vite dev proxy** for developer ergonomics. Follow **Opus's atomic-commit discipline** by isolating the divergence chooser as its own independently-revertible commit (the explicit Chart35 lesson), while inheriting **GPT-5.5's overall commit granularity** for the rest of the work. Harvest the "copy-deployed account+sync skeleton over multi-tenant platform" ADR into `infrastructure-patterns` after the implementation stabilizes, framed per Opus's anti-thesis ("accept N near-identical small services for blast-radius isolation and per-app sync-model freedom") so it's a genuine decision-with-trade-offs rather than restating an obvious choice. Keep the game itself unpinned from the GitHub profile per the career plan; the ADR is the portfolio artifact, the game is the proving ground.
